# Feature: render the notebook views' raw-HTML images inline

## Goal

Reading a `*.ipynb.md` view in Neovim shows the actual image where the document
has one, instead of the text `<center><img src="images/lab_intro.jpg" width=50%></center>`.

Reported against `~/Projects/Courses/CUDA/NsightLab/lab.ipynb.md`, generated by
that repository's `nb2md`, and true for all ten `NsightLab/` views.

## Root cause: four independent layers

Nothing here is a path problem. All 63 image references across the ten views
resolve on disk (0 missing), so no viewer could fail for that reason.

**L1 — the documents use raw HTML, not Markdown image syntax.** Verified with the
real parser on `lab.ipynb.md`:

| form | count across the ten views |
| --- | --- |
| `<img src=...>` | 60 |
| `![alt](...)` | 3 (all in `cvcuda/samples/sharpen_test.ipynb.md`) |

`vim.treesitter.get_parser(buf, "markdown")` classifies those lines as
`html_block` nodes, never as `image` nodes. `nbconvert` copies the notebook cell
verbatim, so this is what the source notebooks contain.

**L2 — `image.nvim` is not loaded in Markdown buffers.**
`dotfiles/config/nvim/lua/plugins/molten.lua` declares it `ft = "python"`, purely
for molten's matplotlib output. A `markdown` buffer has no image backend at all.

**L3 — even loaded, its `markdown` integration would not match.** Its query is
`(image (link_destination) @url)`, i.e. `![alt](path)` only. And
`markview.nvim` never draws real images: for `![]()` it emits an icon extmark,
and for `html_block` it does nothing at all, which is exactly why the raw tag
text is what reaches the screen.

`markdown-preview.nvim` (`<C-n>`) does work today — verified end to end: the
asset route `/__live/asset?p=images%2Flab_intro.jpg&t=<token>` returned 200,
283 861 bytes, byte-identical to the file on disk, and the plugin's index page
rewrites raw-HTML `<img>` tags with the token. That is the browser, not the
buffer, so it is not a substitute for the requested fix.

**L4 — the configured backend cannot work on this machine.** `image.nvim` was
set to `backend = "ueberzug"`, which drives `ueberzugpp layer`. ueberzugpp links
only `xdg_shell` (no `zwlr_layer_shell`), so on a Wayland compositor it opens its
own top-level window instead of drawing at the buffer's coordinates — and a
Wayland client cannot place itself at absolute coordinates at all. Measured: it
logs `[wayland] Canvas created`, then `niri msg windows` lists
`Title: "ueberzugpp_x3j187pb25"` as a normal window while `niri msg layers`
lists no surface belonging to it. The comment that asserted "ueberzug funciona
con cualquier terminal" was wrong.

## Decision

Add one **additive** image.nvim integration for raw-HTML images and load
image.nvim for the Markdown filetypes.

- **A (chosen) — a second integration next to the stock `markdown` one.** The
  stock integration keeps handling `![alt](path)`, `vimwiki`, Quarto and Rmd; the
  new one only scans `html_block` nodes. The match sets are disjoint, so nothing
  is rendered twice, no stock behaviour is disabled, and the stock Markdown query
  does not have to be reimplemented and kept in sync.
- **B (rejected) — replace the `markdown` integration with a superset.** Same
  result, but it means reimplementing and owning the upstream query for
  `![alt](path)` and both shortcut forms, for no gain.
- **C (rejected) — rewrite the tag in `nb2md` so the views emit `![]()`.**
  Destroys the author's centring and sizing attributes, and only moves the
  problem: L2 would still have to be fixed, because image.nvim is not loaded in
  Markdown buffers either way.
- **D (rejected) — browser preview only (`<C-n>`).** Already works, but it is not
  in-buffer reading.

### Placement rule

Each `<img>` tag becomes one match, placed at the **start of its own line**
(`start_col = 0`), not at the tag's column:

- one `html_block` can hold several images (the `<td><center><img .../></center></td>`
  rows in `ncu/step1.ipynb.md`), so a per-block match would stack them;
- the tag column would shift every `<center><img ...>` screenshot right by its
  indent and the image is scaled against the window width
  (`max_width_window_percentage`), so it would overflow the window edge.

### Coupling accepted

The module calls `create_document_integration` from `image/utils/document`, an
internal path of image.nvim, because the plugin resolves integrations by module
name only (`require("image/integrations/" .. name)`) and ships no registration
API. `lazy-lock.json` pins the plugin revision; a future major update may move
that module. Patching the plugin in place was not an option: it lives in the Nix
store.

## Second round: after the first rebuild, still nothing

Two independent causes, found by measurement rather than inspection.

### 1. The rebuild did not deploy the new files

`nixos-rebuild --flake` copies a git worktree **as git sees it**, so untracked
files are excluded. `molten.lua` travelled (tracked, modified) while
`lua/plugins/images.lua` and `lua/image/` did not, leaving a config where
image.nvim was named by a comment and declared by nothing: the plugin stopped
loading even for python.

Proof: `nix flake archive --json` reported the flake source as
`/nix/store/lfphdiqfa5nllc3isgkpsmcmmngld65z-source`, whose
`dotfiles/config/nvim/lua/plugins/` held 23 files and no `images.lua`. After
`git add` of the new paths the same command reported
`/nix/store/4kwzlz9imc4d4sjdnp2ai9z0zafi9v55-source` with both
`lua/image/integrations/nb_html_images.lua` and `lua/plugins/images.lua`
present. Consequence for the workflow: rebuilding to validate uncommitted work
requires at least `git add`.

### 2. The backend was wrong, and the reason recorded for it was false

The claim inherited from `molten.lua` — "WezTerm does not render the kitty
graphics protocol, tested with and without tmux, so ueberzug is the only
option" — does not survive a real probe. L4 explains why `ueberzug` cannot work
here; the table below is why kitty can.

Protocol evidence, collected by writing the query to `/dev/tty` and reading the
reply with bash's `read -N`. An earlier version of the same probe used
`dd | od` and reported a false negative for **every** query, including the DA1
control: `timeout` kills `dd` before its stdio buffer is flushed, so the reply
was read and then discarded.

| Query | Terminal | Reply |
| --- | --- | --- |
| `ESC[c` (DA1 control) | WezTerm, no tmux | `ESC[?65;4;6;18;22;52c` |
| `ESC[c` | WezTerm behind tmux | `ESC[?1;2;4c` — tmux answers for itself |
| `ESC_G … a=q` | WezTerm, no tmux | **`ESC_Gi=1;OK`** |
| `ESC_G … a=q` | WezTerm behind tmux, raw APC | *(nothing — tmux swallows it)* |
| `ESC_G … a=q` | WezTerm behind tmux, DCS passthrough | **`ESC_Gi=2;OK`** |

So WezTerm speaks the protocol **with its default config** — the same query also
answers `OK` from a window started without `--config`, so
`enable_kitty_graphics`, while a real config field, does not need setting — and
tmux forwards it once the escape travels wrapped in DCS passthrough.
`image.nvim` already owns both halves of the tmux story: it refuses to start
without `allow-passthrough` (`tmux show -Apv allow-passthrough`) and wraps its
own escapes in `kitty/helpers.lua`. This server already runs
`allow-passthrough on`.

### Decision: `backend = "kitty"`, and `pkgs.ueberzugpp` dropped

No WezTerm change is needed, so nothing is added to `wezterm.lua`. `ueberzugpp`
leaves `neovimExtraPkgs` because its only consumer is gone; `imagemagick` stays,
since its processor produces the cropped PNGs the kitty backend transmits.

## Third round: which backend, and why the images vanish again

The backend chosen in the second round rendered the images but could not keep
them on screen inside tmux, which the user reported as "they appear by pieces",
"they flicker when I move the cursor" and "I have to hunt for the cursor
position for them to paint". Four candidate causes, tested one at a time.

### Rejected: markview's conceal (my hypothesis, wrong)

`lua/image/renderer.lua:90` only resolves the screen x through conceal when
`conceallevel >= 2`, and `conceal_applies_to_row` consults `concealcursor` and the
cursor row, so the placement looked cursor-dependent by design. markview.nvim sets
`conceallevel = 3` and also forces `wrap = true`. **The user's test killed it:**
`:lua require("markview.actions").detach()` changed nothing. Conceal is not the
cause, and markview stays enabled for these views.

### Rejected: `unicode-placeholders`

The mode is designed for exactly this problem -- it binds the image to placeholder
text cells instead of absolute coordinates, so a redraw re-emits the cells and the
image survives. Measured, it does engage: transmissions carry `U=1` (4 of them),
displays become `a=p,q=2,c=78,r=21,i=5,U=1`, and U+10EEEE placeholder characters
appear in the stream. **But WezTerm does not implement the feature:** it paints
those cells as literal glyphs. The user saw the screen filled with `0`s, images
incomplete, and stray pieces leaking across tmux sessions.

### Chosen: `sixel` inside tmux, `kitty` outside

| Evidence | Value |
| --- | --- |
| `tmux display-message -p '#{client_termfeatures}'` | `...mouse,RGB,sixel,strikethrough,title,usstyle` |
| WezTerm DA1 | `?65;4;6;18;22;52c` -- attribute `4` is sixel, and the binary carries `SixelBuilder`/`SixelData`/`SixelDisplayMode` |
| What image.nvim's sixel backend needs | `magick`, already in `neovimExtraPkgs` |
| Emitted stream with `backend = "sixel"` | 3 DCS sixel sequences for `lab.ipynb.md`, 0 errors |

Because tmux speaks sixel natively it renders it into its own screen model instead
of blindly forwarding a wrapped escape; kitty placements have to travel as absolute
screen coordinates inside DCS passthrough, and every pane redraw desyncs them from
the text. Sixel also drops image.nvim's crop path (`features.crop = false`), which
is what produced the pieces. The user confirmed sixel is stable in tmux and that
`ncu/step1.ipynb.md` (12 images) does not feel slow.

Outside tmux `kitty` stays: nothing rewrites the pane, and it is the sharper of
the two. Hence `backend = tmux and "sixel" or "kitty"`.

### `window_overlap_clear_enabled = true`

The user reported that which-key and other floating UIs went translucent: the image
kept showing through their background. `lua/image/init.lua:213` implements exactly
that option -- for each window, clear the images when it has masks (a float
overlaps it) and re-render them when it does not -- and it is `false` by default.
The default ignore list (`cmp_menu`, `cmp_docs`, `scrollview`, ...) does not
contain which-key, so enabling it clears under which-key.

### The repaint, and what does *not* work

nvim's own redraw writes the blank cells an image occupies, which erases the
pixels the terminal painted there. image.nvim only paints when it believes
something changed, so the image stays erased. Counting the DCS sequences Neovim
writes to the terminal, on `lab.ipynb.md` with `backend = "sixel"`:

| Trigger | DCS sequences | Conclusion |
| --- | --- | --- |
| startup | 3 | baseline |
| `clear()` alone | 3 | the images must be *marked* not rendered, not just cleared |
| `nvim_exec_autocmds("WinScrolled", { file = win })` | 3 | a synthetic WinScrolled does not re-render |
| `nvim_exec_autocmds("BufEnter")` | 5 | works |
| `disable()` + `enable()` | **6** | works, and needs no synthetic events |

`BufEnter` was rejected even though it works: firing it from a `BufEnter` listener
is an infinite loop. The verification harness caught that as a hung process
(`SIGTERM`) before it ever reached the user. The shipped repaint uses
`disable()` + `enable()`, debounced 180 ms on cursor motion inside tmux because
that is when the erase happens, and as a single shot 300 ms after `BufWinEnter`
outside tmux, where only the first paint is wrong.

## Constraints carried over (do not regress)

- Molten keeps `vim.g.molten_image_provider = "image.nvim"` and keeps working; it
  shares whatever backend this spec picks.
- The backend stays conditional: `sixel` inside tmux (tmux renders it natively),
  `kitty` outside (sharper, and no multiplexer to desync it).
- Never `ueberzug`: image.nvim drives ueberzugpp with `layer`, and ueberzugpp has
  no layer-shell support, so it cannot draw at a buffer position under a Wayland
  compositor (L4).
- Never `unicode-placeholders`: WezTerm does not implement the placeholders and
  paints their cells as text.
- `imagemagick` stays in `neovimExtraPkgs`: it is image.nvim's `magick_cli`
  processor, and the sixel backend converts with it as well.
- image.nvim stays lazy. `ft = { "python", "markdown", ... }` keeps it off the
  startup path exactly as before.
- `build = false` stays: the plugin must not try to build itself from the store.
- The spec needs an explicit `config` (lazy.nvim does not call `setup` when
  `config` is present) and that is deliberate: the repaint must install after
  `setup`.

## Follow-ups

- Molten's matplotlib output needs the same visual re-validation as the notebook
  views: it now shares a *conditional* backend, so it takes sixel inside tmux too,
  and it was the original reason `ueberzug` was chosen.
- The `~/Projects/Courses/CUDA` README states that `markview.nvim` and
  `image.nvim` already show the images inline. That was false before this change;
  it is now true for `image.nvim` and still false for `markview.nvim`, so the
  wording needs correcting once the rebuild confirms the behaviour.
- `markview.nvim` renders `![alt](path)` as an icon extmark that sits on top of
  the region image.nvim draws. The sixel backend's crop is disabled and the
  conceal path is not implicated (see the third round), so this is cosmetic, but
  it is worth a look on the three `![png](...)` lines of
  `cvcuda/samples/sharpen_test.ipynb.md`.
- `enable_kitty_graphics` is a real WezTerm config field and the default config
  already answers the kitty query, so it is deliberately not set. If a future
  WezTerm ever needs it, `wezterm.lua` is the place.
- The repaint is a workaround, not a fix: nvim erases the cells an image occupies
  and nothing in image.nvim re-emits on its own. If upstream ever repaints on
  redraw, both the debounced and the single-shot repaint can go.
- The four unverified capabilities of this WezTerm build (kitty placement
  parameters `z`/`C`, the crop form `w=/h=/x=/y=`, and the whole
  Unicode-placeholder feature) could not be probed by reply: WezTerm answers
  `a=q` but stays silent for `a=t`/`a=p`, even for an unknown image id. Anything
  relying on them has to be judged on screen.
