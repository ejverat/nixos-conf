# Feature: native PrusaSlicer on gear5th (Flatpak to nixpkgs)

## Goal

Run PrusaSlicer as a Nix-managed package on gear5th instead of the Flatpak,
keeping the user's existing printer, print and filament presets. Second half of
the "one mechanism for the slicers" backlog item started with OrcaSlicer; FreeCAD
comes after this one proves the approach.

## Context discovered

Everything below was measured before writing any configuration.

**Versions — and why no dedicated pin is needed:**

| Source | prusa-slicer |
| --- | --- |
| Flatpak (`com.prusa3d.PrusaSlicer`) | 2.9.6 |
| Main nixpkgs pin (lock node `nixpkgs_2`, rev `3ed67ec0`) | **2.9.6** |
| `nixpkgs-orca` pin (`e554fab`) | 2.9.6 |

**Exact parity with the Flatpak, from the main pin** — so there is no version
tradeoff to weigh at all.

A trap worth recording, because it produced a wrong conclusion first: in this
lock the root's `inputs.nixpkgs` maps to the node named **`nixpkgs_2`**, not to
the node named `nixpkgs`. Reading `nodes.nixpkgs` yields rev `3e41b24`, which is
some *dependency's* nixpkgs and reports 2.9.5 — a plausible-looking number that
has nothing to do with this host. Resolve the pin through
`nodes.<root>.inputs` rather than guessing the node name; the built store path
(`prusa-slicer-2.9.6`) is what exposed the mistake.

Compatibility was never the constraint anyway: `PrusaSlicer.ini` declares
`version = 2.9.3` and the presets were generated by PrusaSlicer 2.9.3, so this
build opens older config regardless, and the presets carry no version field.

**What the user actually has in the Flatpak** (3.6 MB of config, all hand-made
for a Kingroon KP3S Pro S1):

| Directory | Files |
| --- | --- |
| `printer/` | 1 — `Kingroon KP3S Pro S1.ini` |
| `print/` | 3 — `KP3S Pro S1 Standard`, `Kingroon KP3S Pro S1`, `… fast` |
| `filament/` | 2 — `Kingroon KP3S Pro S1 (PETG)`, `(PLA+2)` |
| `physical_printer/` | 1 |
| `sla_print/`, `sla_material/`, `vendor/`, `shapes/` | 0 |

`PrusaSlicer.ini` holds ordinary host paths (`~/LDATA/...`, `~/Downloads`) and
**no sandbox paths** — no `.var/app` and no `/app/` prefix appears anywhere — so
it is portable to a native build. It has no preset-folder reference either, which
means it does not point at the Flatpak's config location.

## Decisions

- **Use the main nixpkgs pin.** It already ships 2.9.6, exactly matching the
  Flatpak, and it is the same pin every other application on this host uses
  (gimp, libreoffice, chromium). The `nixpkgs-orca` pin exists only because
  OrcaSlicer lagged a *minor* version (2.3.2 against 2.4.2): it is the exception,
  not the pattern, and adding a second consumer to a pin named after a different
  application would either make that name a lie or force a rename of merged code.
- **Migrate presets and `PrusaSlicer.ini`, but not `cache/`.** The cache is
  transient, and the `.ini` is what carries the user's preferences. Window
  geometry and recent-file lists ride along, which is the same tradeoff accepted
  for OrcaSlicer's config.
- **Back up before touching anything**, in a dated directory outside the
  repository, and verify the copy file by file — the pattern used for the
  OrcaSlicer profiles.
- **No GTK work needed.** gear5th's global `flake.homeModules.gtk` (Nordic plus
  `prefer-dark`) already applies to every GTK 3 application, and PrusaSlicer is
  GTK 3. OrcaSlicer needed a per-app workaround only because the global config
  was broken at the time; it is not.
- **The Flatpak stays** until the native build is validated, exactly as with
  OrcaSlicer. Removing it is a separate, later decision.

## Tasks

1. Vendor nothing yet; migrate the live config.
2. Add `modules/features/prusaslicer.nix` with `flake.homeModules.prusaslicer`
   and `flake.nixosModules.prusaslicer`.
3. Register the home module in gear5th.
4. Back up and migrate the Flatpak config to the native path.
5. Build, then verify the application reads the migrated presets.
6. Commit and ship through the issue-first PR flow.

## Risks

- **The native data directory is confirmed.** `~/.config/PrusaSlicer` was the
  strong inference — the real binary references `XDG_CONFIG_HOME` and
  `PrusaSlicer.ini`, and its fork OrcaSlicer uses `${XDG_CONFIG_HOME}/<app_name>`
  — but it could not be observed from the CLI, since `--help`, `--info` and
  `--save` all complete without initialising it. The first GUI launch settled it;
  see the evidence below.
- Presets written by the Flatpak may reference vendor profiles that the Flatpak
  bundled and the nixpkgs build packages differently. Addressed by loading a
  preset, not by assuming; see the evidence below.
- The `.ini` carries window geometry tuned for the Flatpak's window; harmless but
  it may open oddly on first launch.

## Verification evidence

Backup, taken before touching anything:

- `~/backups/prusaslicer/<timestamp>/` holds the Flatpak's `config` and `data`
  (4.0 MB). `SHA256SUMS` covers 141 files and verifies, plus a `MANIFEST.md` with
  restore commands. The checksum file initially hashed itself — the same
  self-reference bug as the OrcaSlicer backup — and was regenerated excluding
  itself.

Package:

- `bin/prusa-slicer` is a **16 KB compiled wrapper** whose real binary is
  `bin/.prusa-slicer-wrapped` (43 MB), the same shape as OrcaSlicer's and the
  same reason `wrapProgram` must never be used on it. Recorded in the module.
- Version **2.9.6**, exact parity with the Flatpak, from the main pin. Closure:
  **1508 MiB** unpacked — the pin is shared with every other application here.

Migration:

- 9 files / 84 KB into `~/.config/PrusaSlicer`, being 7 user presets plus
  `PrusaSlicer.ini` and `ArchiveRepositoryManifest.json`. The 3.6 MB apparent
  size in the Flatpak was mostly `cache/`, which was deliberately excluded.
- The two local files the presets reference exist: a custom bed STL and an SVG
  texture under `~/LDATA/3DPrint/KP3SProS1/`.

Loading a migrated preset (the check that matters):

- `prusa-slicer --load ~/.config/PrusaSlicer/printer/"Kingroon KP3S Pro S1.ini" --save`
  exits 0 and produces **11632 bytes** against the **9957-byte** default for the
  same command without `--load`. The preset's settings are therefore read and
  applied by this build.
- The presets carry a `# generated by PrusaSlicer 2.9.3` header, so this 2.9.6
  build is loading older config — which is the normal path, not an edge case.

Negative and inconclusive results, recorded so they are not re-run as if they
were successes:

- **The default data directory could not be observed from the CLI** — `--help`,
  `--info` and `--save` all finish without initialising it, and a scratch `HOME`
  stayed empty in every attempt — so it was carried as an inference rather than
  a claim. The first GUI launch then **confirmed it**: the application wrote into
  `~/.config/PrusaSlicer`, creating `cache/` (4.8 MB of vendor indices and
  thumbnails), `workflows.json`, and an updated `PrusaSlicer.ini`, all within the
  same minute. The 7 migrated presets were left untouched beside them.
- That the application rebuilt `cache/` on first launch also validates excluding
  it from the migration: it is derived state, not user configuration.
- **`--load` with three presets at once segfaults** (exit 139) while one preset
  works. Left alone: it is CLI fragility, not a packaging regression, and the
  supported path works.
- **The Flatpak comparison for that crash is unusable.** The same command
  through `flatpak run` produced no output file in either attempt, so it cannot
  be used to argue the crash is upstream-only. Stated as inconclusive rather than
  claimed as evidence.
